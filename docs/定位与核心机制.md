# CodexForge 定位与核心机制

> **一句话定位：一个能啃超长程任务的 general coding agent。**
> 两个核心能力：**自主反馈**（不靠模型自评，靠确定性证据）与**代码整洁度**（可量化、可收敛）。

---

## 一、为什么选这两个点（而不是别的）

### 1.1 现在 coding agent 的真实短板在哪

按「模型能力已经很够，工程还没跟上」这个判断切分，短任务基本被解决了：

| 任务长度 | 现状 | 瓶颈 |
|---|---|---|
| 单文件、几十行 | 已解决 | 模型能力 |
| 多文件、几百行 | 基本可用 | 需要人工检查 |
| **跨天、上千行、需重构** | **普遍失败** | **不是模型笨，是反馈机制缺失** |

失败不是「模型不会写」，而是这三种：

1. **绕圈**：同样的错反复犯，因为上下文压缩把失败记忆丢了
2. **伪完成**：声称做完了，但验收项没满足，且没人验证
3. **越改越脏**：每轮加功能，没人管代码质量，最后不可维护

**这三条恰好都不是模型能力问题，而是 harness 缺失。** 所以选这两个点。

### 1.2 与主流方案的差异

| 方案 | 长程反馈 | 整洁度 | 缺陷 |
|---|---|---|---|
| 裸 CLI（codex / claude-code） | 靠模型自觉 | 无 | 绕圈无法自纠 |
| 单轮 wrapper（多数开源） | 无 | 无 | 只包装了调用 |
| 判官类（Agent-as-a-Judge） | LLM 自评 | 无 | 自评不可靠、不可审计 |
| **CodexForge** | **确定性证据 + 跨轮状态** | **AST 度量 + 净改善门** | — |

**最关键的区别：我们的反馈信号不是 LLM 给的，是代码事实给的。**
文件在不在、测试过不过、AST 有几个 smell —— 这些不依赖模型判断，
所以可复现、可审计、可断言。

## 二、核心机制一：长程自主反馈

### 2.1 三路反馈信号（都不用 LLM 判断）

| 信号 | 来源 | 判定方式 |
|---|---|---|
| **目标达成** | `Task.verify()` | 文件存在 / 测试退出码 / 全部文件齐全 |
| **代码整洁度** | `quality.evaluate()` | AST 指标 → 0-100 分 |
| **工作区进展** | `workspace_fingerprint()` | 内容哈希，排除缓存目录 |

三路各管一件事：目标管「做没做完」，整洁度管「做完得干不干净」，
指纹管「有没有真的在动」。

### 2.2 跨轮记忆：解决「上下文压缩丢记忆」

核心问题：长任务必然经历上下文压缩，而压缩会丢掉「试过什么、为什么失败」。

解法：把方向与教训**外置到磁盘**，每轮重启时注入。

```
.opencode/target_state.json
├── target              目标原文
├── directions[]        每个尝试方向：{text, outcome, failure_reason, turn}
├── lessons[]           教训（最多 8 条，去重）
├── fingerprints[]      最近 10 轮的工作区指纹
└── stagnation_count    连续停滞计数
```

注入格式（重启时进 prompt）：

```markdown
## 已失败的方向（不要重复）
- 用正则解析 CSV → 失败：引号内逗号处理不了
- 直接 sed 替换 → 失败：破坏了缩进

## 教训
- 第 3 轮声称完成但目标未达成：test_calc.py 不存在
```

**这是可审计的**：答辩时能直接展示「agent 在第 7 轮试过 X，失败原因是 Y，
之后 12 轮没有再试」—— 而模型侧 memory 是一个黑盒。

### 2.3 停滞检测阶梯

连续检测工作区指纹不变，按严重度递进：

| 次数 | 动作 | 注入的指令 |
|---|---|---|
| 0 | 正常 | — |
| 1 | 提醒 | 「本轮没有实质变化，确认你在推进而不是在分析」 |
| 2 | 强制换策略 | 「必须放弃当前方案，改用不同的实现路径」 |
| 3 | 重启 | 「判定为绕圈，会话重启，只保留目标与已失败方向」 |

**为什么用阶梯而不是直接重启**：重启成本高（丢上下文），
过早重启会浪费已积累的探索。阶梯给模型两次自我纠正机会。

### 2.4 一个反直觉的设计：不给模型看「成功了多少」

prompt 里只出现**失败与待办**，不出现「已完成 N 项」。

理由：模型看到「已经做了很多」会有收尾倾向，而长程任务里这个倾向是致命的 ——
它会让 agent 在 70% 完成度上停下。

## 三、核心机制二：代码整洁度

### 3.1 为什么自己写 AST 度量而不用 ruff/pylint

赛道评分看「可复现性」。第三方 linter 的版本漂移会让同一份代码在不同机器上
给出不同结果 —— 而整洁度如果作为**验收门**，必须确定性且可逐项解释。

因此：只用 `ast`，规则自定，版本无关。外部 linter 保留在「建议层」，
本模块在「判定层」。

### 3.2 七个指标（都满足：可计算、可归因、有阈值）

| 指标 | 严重度 | 为什么算「脏」 |
|---|---|---|
| `long_function` | medium/high | >60 行难测难懂；>120 行直接判 high |
| `deep_nesting` | medium | >4 层嵌套，认知负担陡增 |
| `unused_import` | medium | 死代码，且掩盖真实依赖 |
| `bare_except` | **high** | 吞掉 KeyboardInterrupt/SystemExit，真实缺陷 |
| `dead_assignment` | low | 赋值未用，通常是重构残留 |
| `duplicate_branch` | medium | if/elif 分支体相同，条件写错或可合并 |
| `todo_marker` / `long_line` | low | 提示级 |

**刻意不做的指标**：
- 圈复杂度：对 LLM 生成的代码区分度低（它天然爱写长函数），阈值难定
- 命名风格 / 注释率：**高注释率不等于干净**，反而常是代码不自解释的信号

### 3.3 跨文件重复检测：AST 结构指纹

LLM 有个稳定坏习惯：遇到相似需求就复制粘贴改两个变量名。
单文件看每处都合理，全局看就是灾难。

实现：提取函数 token 序列（标识符与字面量归一化），用
`difflib.SequenceMatcher` 算相似度。

**踩过的坑（关键）**：初版用集合 Jaccard，**完全忽略频次**。
实测「1 个 for 循环」vs「5 个相同结构的 for 循环」，token 集合完全相同，
Jaccard = 1.0（判为完全重复），实际相似度只有 0.467。
改用 SequenceMatcher 后误报消失。

**这个 bug 值得单列**：它说明「度量工具本身也需要被验证」。
如果一个整洁度指标会误报，agent 就会被要求去「消除并不存在的重复」，
净效果是负的。

### 3.4 净改善门：防止越修越脏

这是整洁度机制最关键的一环。**如果 agent 的改动被无条件接受，
「整洁度提升」就是自我欺骗。**

```
每轮：
  1. 快照当前 .py 文件
  2. agent 改动
  3. 重新评估
  4. 门判定：
     - 分数下降 → 回滚
     - 改善 < 0.5 分 → 回滚
     - 引入新 high 级问题 → 回滚
     - 否则接受
```

**收敛判定用「改善速率」而非绝对分数**：
简单的 `score >= 90` 有两个问题 —— 95 分里那 5 分往往是主观风格，
强行改会伤害可读性；有时间预算时「性价比」比「绝对分数」重要。

### 4.1 整洁度机制（本地，零 token）

```
得分：86.8/100
问题分布：
  long_function    9  [medium]
  unused_import    8  [medium]
  deep_nesting     4  [medium]
  todo_marker      3  [low]
  dead_assignment  2  [low]

重复代码：69 个函数中检出 2 对（5.8%）
  gateway/client.py:54 _post_json() ≈ harness/compat_proxy.py:206 _upstream_post() (0.78)
```

## 五、踩坑清单（这些都写进代码注释了）

| 现象 | 根因 | 修复 |
|---|---|---|
| `stream disconnected before completion` | codex 以流式消费 Responses API，代理返回整包 JSON | 实现完整 SSE 事件序列（`response.created` → `output_text.delta` → `response.completed`） |
| 模型回复「sandbox is read-only」拒绝写文件 | `codex exec` 非交互模式下 `workspace-write` 被理解为只读 | 改 `danger-full-access`，安全由外层目录隔离承担 |
| codex 卡 61.8 秒 | 默认 CODEX_HOME 刷 ChatGPT token，受限网络 403 重试 | 隔离 CODEX_HOME 且不复制 `auth.json` → 4.4 秒 |
| `messages` 永远为空 | codex 真实消息在 `item.completed` 的 `item.text` | `CodexEvent.item/item_type/is_message` |
| 整洁度把 `__future__` 报为未使用 | import 分析没区分结构性命中 | 白名单 `__future__.*` |
| 快照目录污染整洁度评分 | 评估没排除 `.cforge` | 加入排除列表 |
| 快照目录自我复制导致文件指数增长 | `_snapshot` 把自己的输出又扫进去 | 排除 dest 本身 |
| 不同方向被判为重复 | 归一化正则要求 3 字符，数字被丢弃 | 保留所有 token + 补足停用词 |
| 最后一轮的伪完成声明丢教训 | 教训记录放在终止判断之后，被 break 跳过 | 移到终止判断之前 |
| **4 个文件内容正确却全部「语法错」** | **agent 写出 UTF-16 编码（带 BOM），不是 UTF-8** | 编码问题单独检测并报告，不混入语法错 |
| **目标判「已达成」但代码一行都跑不了** | **`file_exists` 只看文件在不在，不看能否解析** | 增加可解析性检查，UTF-16 / 语法错都不算达成 |

### 最后两条是这一轮最有价值的发现

它们合起来说明一件事：**「文件存在」是最弱的验收标准**。

实测的真实序列：
1. agent 创建了 4 个文件，逻辑完全正确（`add`/`sub`/`unittest` 都写对了）
2. 但全部是 **UTF-16 编码**
3. 旧的 `file_exists` 检查 → 判「目标达成 ✅」
4. 旧的整洁度检查 → 报 4 个「语法错」，但没说为什么

**这是双重失效**：验收把一个跑不了的交付物判为成功，
而反馈又把病因说错了（不是语法问题，是编码问题）。

修复后的诊断：
```
- calc/add.py 无法解析：UTF-16 编码（含 BOM），需转为 UTF-8
```
agent 拿到这条，一次就能改对。**反馈的价值不在于「有问题」，
而在于「指向真病因」**。
