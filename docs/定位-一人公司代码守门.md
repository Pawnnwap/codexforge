# CodexForge 定位：一人公司的代码守门

> 这份文件回答一个问题：**「给程序员/一人公司用」算不算合格的垂直定位。**
> 结论：不算，需要收窄到具体动作。下面是推导过程与最终定位。

---

## 一、为什么「给程序员用」不合格

Track 160 的实用性占 **40%**，原文拆成三项：

> 实际问题解决能力、**场景适配度**、市场/科研价值匹配度

「给程序员用」在第二项上拿不到分，理由很直接：

**所有 coding agent 默认都是给程序员用的。** Claude Code、Cursor、Codex、Aider、
Cline 全都如此。所以这不是垂直定位，是**品类定义**。

评委必然会问：「和 Cursor 有什么区别？」如果答「我的长程反馈更好、代码更整洁」，
那说明的是**技术差异化**，不是**场景垂直化**。这两件事在评分表里落在不同格子：

| 说法 | 落在哪个格子 | 能拿多少 |
|---|---|---|
| 「我给程序员做 coding agent」 | 场景适配度 | 拿不到 |
| 「我的长程反馈机制比现有方案强」 | 技术实现难度 30% | 能拿 |

而 160 现在 **154 队**（上次查询 152，还在涨），在这个池子里只靠技术差异化
很难脱颖而出 —— 因为参赛队伍里技术强的太多了。

---

## 二、「一人公司」方向对，但还不够

「一人公司」比「程序员」好，因为它隐含了一个真实约束：**没有人做 code review**。

这是硬约束，不是描述。大公司有 review 流程、有 CI 门禁、有技术债专项；
一人公司什么都没有，代码质量完全取决于个人自律 —— 而人在赶 deadline 时，
自律必然让位于交付。

但「一人公司」仍然是个大框：注册公司、记账报税、写代码、做客服、跑运营。
如果产品只做其中一件（coding agent），那用户画像收窄了，场景仍然没收窄。

所以还要往下收一层：**在一人公司的所有工作里，哪一件和「长程反馈 + 整洁度」直接相关？**

答案只有一件：**长期维护自己的代码库**。

---

## 三、最终定位

> **给同时维护多个项目的独立开发者 / 一人公司，做无人值守的代码质量守门与持续重构。**

### 三个要件逐一核对

| 要件 | 这个定位的回答 |
|---|---|
| **具体的人** | 同时维护 3-10 个项目的独立开发者、一人公司技术负责人 |
| **具体的痛** | 没人 review，重构永远排在功能后面，代码必然腐化；等到想改时已经不敢动 |
| **通用工具搞不定** | Cursor/Claude Code 是「你叫它才动」的交互式工具，没人会每天主动说「帮我清一下技术债」 |

第三条是关键。**通用 coding agent 的形态是「被动响应」，而这个痛点的本质是「需要主动持续」。**
这不是模型能力问题，是产品形态问题。

### 为什么两个核心机制在这里是刚需而非锦上添花

| 机制 | 在这个场景里为什么必需 |
|---|---|
| **长程自主反馈** | 重构一个大文件、消除跨文件重复，天生是多轮迭代，单轮做不完。而且没有人在旁边看着，agent 必须自己判断「改好了没有」 |
| **代码整洁度** | 这里整洁度**就是**业务指标本身，不是附加功能。守门守的就是这个 |

这比「general coding agent」的论证强得多 —— 在通用场景里，这两个机制是「更好的实现」；
在这个场景里，它们是「没有就不成立」。

### 可量化的价值主张

一人公司最缺的是**可对外证明的东西**。所以价值必须能落成数字：

```
守门报告（自动产出，可贴进 README 或投资人材料）
├── 整洁度 67.6 → 91.2 (+23.6)
├── 累计检查 240 次，实际动手 18 次
├── 改动被接受 15 次，被回滚 3 次
└── 当前 0 个 high 级问题，重复代码率 2.7%
```

这不只是「我写了个 agent」，而是**「我的代码库在过去 N 周里质量提升了 X」**——
对一人公司来说，这是能拿去谈客户、谈融资、招人的凭证。

## 四、产品形态必须跟着改（已完成）

定位是「守门」，形态就不能是「我每次手动跑一下」。

| | CLI 形态 | 常驻守门形态（已实现） |
|---|---|---|
| 触发 | 用户手动 | 四道闸门自动判定 |
| 频率 | 想起来才跑 | 持续，但有冷却 |
| 产出 | 屏幕输出 | 落盘报告（人看 + 机器读） |
| 与定位 | **自相矛盾** | 一致 |

### 四道闸门（`cforge/watch/trigger.py`）

常驻服务的成败全在「何时动手」：

1. **冷却闸**：默认 10 分钟。更频繁会打断心流，更稀疏则一天只跑几次，价值感低
2. **变更闸**：只看源码文件，改 README 不触发代码重构
3. **债务闸**：整洁度 < 80 或有 > 2 个 high 级问题才动手。90 分的代码不需要「重构」
4. **冲突闸**：变更超过 25 个文件时跳过 —— 用户正在大改，插进去等于制造冲突

**每个判定都必须给出人能看懂的理由**。黑盒守护进程没人敢用 ——
用户会问「为什么现在跑」或「为什么一天没动」，答不上来就会被卸载。

## 六、这一轮修掉的产品级缺陷

常驻守门不是「把 CLI 套个 while 循环」那么简单。以下三个缺陷都是实测中暴露的，
全部是「用户会用一次就卸载」的级别。

### 6.1 报告会谎报质量下降（最严重）

**现象**：某次运行全部跳过（无源码变更），报告却显示：

```
质量：83.8 → 75.0 (-8.8)
```

**根因**：`83.8` 是历史基线，`75.0` 是上次运行后的值，本次根本没做事。
把两个跨会话的数字放在一起对比，等于告诉用户「你不在的时候代码变差了」。

**修复**：会话内统计与历史累计彻底分开。

```
本次检查 1 次，实际执行 0 次
本次未执行改动：无源码变更
历史累计：检查 5 次，执行 2 次，接受 1 / 回滚 1
基线 → 当前：83.8 → 75.0
```

这类缺陷在常驻服务里是致命的 —— 用户会持续读到误导性数据，然后失去信任。

### 6.2 「100 分」但两个函数一模一样

**现象**：守门把 unused import 全清掉后报告 `100/100`，
但项目里有两对函数是复制粘贴改名（相似度 1.00）。

**根因**：跨文件克隆检测**没有纳入评分**。它是个独立能力，
`evaluate()` 只算单点 smell。

**修复**：把重复率纳入评分，并在报告里单列「剩余债务」：

```
## 剩余债务（当前自动修复器无法处理）
以下问题仍在，是当前分数无法提升的原因：

**2 对跨文件重复函数**（重复率 100.0%）—— 需要合并抽象，
确定性修复器无法安全处理。

→ 用 --fixer codex 让 LLM 处理，或人工重构。
```

这里的设计判断：**「检测到但修不了」必须明说**。
让用户以为已经干净，比不检测更糟。

### 6.3 克隆检测阈值是拍脑袋定的

**现象**：`save`（INSERT）与 `load`（SELECT）被判为相似度 0.76，
误报为重复代码。

**根因**：初始阈值 0.72 是凭感觉设的，没有用真实代码校准。

**校准过程**（在 demo 项目上实测）：

| 阈值 | 检出 | 内容 | 判定 |
|---|---|---|---|
| 0.72 | 6 对 | 含 `save~load`（0.76） | ❌ 语义不同被判重复 |
| 0.80 | 2 对 | 只有真复制 | ✅ |
| 0.90 | 2 对 | 只有真复制 | ✅ |
| 1.00 | 2 对 | 只有真复制 | ✅ |

在 cforge 自身（3.5k 行）上交叉验证：阈值 0.72 会把 `_snapshot~_restore`
判为重复，但这两个是方向相反的操作。

**最终参数**：`min_statements=4` + `minsimilarity=0.90`。
同时引入样本量置信度 `sqrt(n/6)` —— 只有 2 个函数时，1 对重复
不该被当作「100% 重复率」。

**教训**：度量工具的阈值必须用真实代码校准。阈值错了，
agent 会被要求去消除**并不存在**的重复，净效果为负。

### 6.4 「只有重复代码」的项目拿不到修复指令

**现象**：项目里只有跨文件重复、没有单点 smell 时，
`build_fix_prompt()` 返回空字符串，codex 修复器**永远不会被调用**。

**根因**：prompt 只从 `report.smells` 生成，而重复对不在 smells 里。

**这是一个自相矛盾的失效**：报告告诉用户「用 `--fixer codex` 处理重复」，
但修复器收到空 prompt 直接返回 False。

**修复**：prompt 同时覆盖两路债务：

```
## 单点问题（共 N 处）
- `a.py:1` **unused_import** — `os` 未被使用

## 跨文件重复（共 1 对）
抽取共用函数消除重复。注意：
- 保持每个原函数的公开签名和外部行为不变
- 不要删除任何原有函数名，调用方可能依赖

- `store.py:1` **save()** 与 `store.py:8` **save_cache()** 高度重复（相似度 1.00）
```

### 6.5 免费模型跑不动 codex 的真实负载（环境约束）

**现象**：`cohere/north-mini-code:free` 面对 codex 的 17K 系统提示词 + 7 个工具定义，
300 秒内完成不了一次完整 turn。上游返回 200，proxy 正常转发，
但 codex 侧超时。

**根因**：模型能力/推理速度限制，不是架构缺陷。

**这条要写进文档而不是隐藏**：它说明「免费模型能用」这个假设在
codex 的真实负载下不总成立。生产环境必须用书生或付费模型。

### 6.6 codex 会把本机所有技能注入系统提示词（最重要的发现）

**现象**：模型回复「你提到了 'the following issues' 但还没列出来」，
它根本没读到我们 554 字符的任务描述。

**抓包证据**（实际发往上游的 4 条消息）：

| # | role | 长度 | 内容 |
|---|---|---|---|
| 0 | developer | 17,174 | codex 自身的行为准则 |
| 1 | developer | **7,367** | **本机 `~/.agents/skills` 下 20+ 个技能的描述** |
| 2 | user | 464 | 环境上下文（cwd、shell、时区） |
| 3 | user | 554 | **我们真正要执行的任务** |

第 1 条里混入了「微信视频号下载、解密」「竞赛答辩」「LaTeX 论文」
等与本任务完全无关的技能说明。

**这是竞争环境下的系统性劣势**：任务描述被淹没在 25K 字符里，
小模型的注意力被严重稀释，表现为「读不到指令」「跑到无关方向」。

**已尝试且无效的方案**：
- `CODEX_HOME` 隔离（已做，但技能目录读的是 `$HOME/.agents`）
- `HOME` / `USERPROFILE` 重定向（codex 内部解析，无效）
- `-c features.skills=false`（无此开关）
- `--ignore-rules`（只忽略 execpolicy rules，不影响 skills）

**当前对策：prompt 结构改造**——用显式分隔线把任务标成「唯一任务」，
并显式声明「忽略无关技能说明」：

```
============================================================
【唯一任务】以下是本次要执行的完整任务，请只关注这一块内容。
忽略上下文中任何与代码整洁度修复无关的技能说明或历史对话。
============================================================

工作区：`...`
### 跨文件重复（1 对）
- `store.py:1` save() 与 `store.py:8` save_cache() 高度重复（1.00）
### 约束
...

============================================================
【任务结束】现在开始执行上面的任务，直接修改文件。
============================================================
```

**顺序也调整了**：问题清单在前、约束在后。实测约束放最前时，
模型容易把约束当「背景说明」而漏读问题清单。

**这是一个诚实的限制**：我们无法从外部关闭这个注入（除非改 codex 源码），
只能靠 prompt 工程缓解。生产部署时建议用干净的 `HOME` 运行。

## 七、实测验证（真实运行，非设计意图）

### 5.1 完整守门链路

```
$ python -m cforge.cli guard --workspace ./demo-guard --debt-score 99 --cooldown 0

修复器：scripted（AST 确定性，零 token）
  [guardian] 触发：整洁度 89.2 低于 99.0
  [guardian] ✓ 89.2 → 100.0 (+10.8)，修复 4 处，新增 0 处

质量：89.2 → 100.0 (+10.8)
```

修复前：
```python
import os
import sys
import json
import re
import time

def parse(text):
    data = json.loads(text)
    ...
```

修复后：
```python
import json

def parse(text):
    data = json.loads(text)
    ...
```

**业务逻辑（`json.loads`、`if 'items' in data`）完好无损**，只精确删掉了 4 个未使用 import。

### 5.2 幂等性验证

第二次运行：
```
[guardian] 跳过：债务未达阈值
```

不会反复改动已修好的代码 —— 这是常驻服务能被接受的前提。

### 5.3 闸门单测覆盖

35 个 `test_watch.py` 用例，重点覆盖「**不该跑的时候真的不跑**」：

- 冷却期内不跑
- 只改文档不跑
- 缓存目录变动不跑
- 债务未达阈值不跑
- 用户大改时不跑
- 连续失败触发熔断
- 状态跨重启可恢复

## 六、形态已就位，但仍缺的三件事

诚实列出（这些是答辩会被追问的）：

| 缺口 | 影响 | 补法 |
|---|---|---|
| **书生真实接入** | 赛道硬性要求「必须基于书生大模型」，现在跑 OpenRouter | 拿 key，`CFORGE_BACKEND=intern` 即切（provider 抽象已就绪） |
| **真实用户案例** | 「一人公司」是推断的痛点，没有真人用过 | 找 1-2 个独立开发者朋友实测一周，拿守门报告 |
| **多语言修复器** | AST 确定性修复只覆盖 Python 的 unused_import | codex fixer 已支持任意语言，但需真实验证 |

第一条是硬门槛，优先级最高。

---

## 七、一句话总结

**「给程序员用」是品类，「给一人公司的长期代码库做无人值守守门」才是定位。**

差别在于：前者需要靠技术深度赢过 153 个对手，后者只要证明「这个痛点真实、
这个形态对、这个效果可量化」—— 而后者恰好是 CodexForge 两个核心机制
唯一能当「刚需」而不是「加分项」的场景。
