# 跨文件重复消除流程

重复代码是"最该修的一类技术债"——改一处忘另一处是经典事故源。
但消除重复也是**最容易改坏**的操作，所以流程的重点是约束，不是技巧。

## 前置：确认真的是重复

检测阈值（实测校准，不要凭感觉调）：

- min_statements=4：短于此的函数不值得比（样板代码会误报）
- similarity=0.90：0.72 会把 `save`(INSERT) 与 `load`(SELECT) 判为重复
  ——它们只是"都是数据库操作"，语义完全不同

## 安全重构五条硬约束（来自实测修复会话）

1. **保持每个原函数的公开签名和外部行为不变**
2. **不要删除任何原有函数名**——调用方可能依赖；新抽象与旧函数并存，
   旧函数改为委托即可
3. 文件保持 UTF-8 编码（实测有 agent 产出 UTF-16 导致跑不了的案例）
4. 只做重复消除，不做无关的"顺手优化"
5. 改动最小优先：先抽函数，不急着设计"正确的抽象"

## 执行后的验证（净改善门，三条全过才接受）

- 整洁度分数不降
- 改善 ≥ 0.5 分
- 无新增 high 级问题

任一不过 → **全部回滚**。回滚是设计内的正常路径，不是失败。

## 典型形态

实测案例：`save_cache` 改为 `return save(conn, key, value)`——
保留原函数名、签名不变、UTF-8，完全遵守五条约束。

```
重构前：store.py 的 save() 与 save_cache() 相似度 1.00
重构后：save_cache 委托 save；原函数名与签名保留
结果：重复率 100% → 0，净改善门通过，耗时 2m11s
```

## 何时不动手

- 只有 1-2 个函数的小文件里检出 1 对：样本量置信度
  `sqrt(n/6)` 太低，"重复率 100%" 是统计假象，不修
- 两个函数只是结构像、语义相反（如 save/load、快照/恢复）：误报，不修
