# 技术债务三档分类

守门报告列出的问题，按**谁能安全地修**分三档。分档的目的是不让用户
以为"检测到 = 已修复"，也不让自动修复器碰它不该碰的东西。

## 三档定义与处理

### 第一档：确定性自动修（零 token，零风险）

- unused_import（未使用的 import）
- 典型场景：分数 75-90 的"亚健康"项目

处理命令：

```bash
python -m cforge.cli guard --workspace <目录> --fixer scripted --max-cycles 1
```

AST 精确删除，业务逻辑不动。实测：89.2 → 100.0，只删 4 个未使用
import，`json.loads` 等逻辑完好无损。修完自动过净改善门
（分数下降/改善<0.5/新增 high → 全部回滚）。

### 第二档：LLM 修复（跨文件重复等结构性债务）

- 跨文件重复函数（相似度 ≥ 0.90 的对）
- 单一确定性规则搞不定、但方向明确的重构

处理命令：

```bash
export OPENROUTER_API_KEY=sk-or-...   # 或 INTERN_API_KEY（书生）
python -m cforge.cli guard --workspace <目录> --fixer codex --cooldown 600
```

给 codex 的 prompt 必须带 5 条硬约束（实测总结，缺一不可）：
1. 保持每个原函数的公开签名和外部行为不变
2. 不要删除任何原有函数名（调用方可能依赖）
3. 文件保持 UTF-8 编码
4. 只做重复消除，不做无关"顺手优化"
5. 改动最小的方案优先

修完同样过净改善门；回滚是默认动作不是失败动作。

### 第三档：人工（当前工具明确不碰）

- 架构级问题（循环依赖、职责混杂）
- 需要领域知识才能决定"哪个抽象是对的"
- 报告"剩余债务"里列出的项

对这一档，**正确输出是解释为什么自动修不了**，而不是硬修。
让用户以为已经干净，比不检测更糟。

## 汇报格式

```
债务总计 N 处：
- 第一档（可自动修）：N1 处 → 已用 scripted 修复器处理，A → B
- 第二档（LLM 可修）：N2 处 → 已用 codex 修复器处理 / 待处理（原因）
- 第三档（需人工）：N3 处 → 清单 + 为什么自动修不了
```
