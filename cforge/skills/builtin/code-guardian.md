# 代码守门评估

对一个代码目录做一次完整的质量评估，并把报告解读成人能决策的结论。

## 触发条件

- 用户要求"评估/检查这个项目的代码质量"
- 用户问"这个仓库干不干净 / 有多少技术债"
- 守门流程的第一步（先评估，再决定动不动手）

## 执行步骤

1. **评分**（确定性，不调 LLM，零成本）：

   ```bash
   python -m cforge.cli quality --path <目录> --verbose
   ```

   输出 0-100 分、问题分布（high/medium/low）、跨文件重复率。

2. **读分规则**：
   - ≥ 90：健康。不需要重构，不要为动而动。
   - 80-90：正常在写代码的区间。记录，不动作。
   - < 80 或 high > 2：达到守门债务阈值，进入修复流程（见 debt-triage）。

3. **重复代码单独看**：重复率是全局指标，不和单点 smell 混在一起讲。
   实测校准阈值：min_statements=4 + similarity=0.90（0.72 会把
   `save`(INSERT) 和 `load`(SELECT) 误判为重复）。

## 报告解读（必须说的三件事）

1. 分数是多少，相对基线变化了多少（**只对比本次会话内真跑过的**——
   跨会话对比历史基线会造成"跳过却显示质量下降"的误导，实测踩过）；
2. 剩余债务是什么、为什么当前修复器处理不了（检测到但修不了必须明说）；
3. 下一步建议：能自动修 / 需 LLM 修 / 需人工，三档分类见 debt-triage。

## 禁忌

- 不要为凑动作而重构 90 分以上的代码——守门的价值在"不该动时不动"。
- 不要把历史累计和本次会话的变化混为一句话汇报。
